## كيف يصير المتصفح منفّذاً لكود المهاجم؟

البرمجة النصية عبر المواقع (Cross-Site Scripting, XSS) بتظهر لما بيانات يسيطر عليها المهاجم تنعرض بصفحة الموقع كأنها كود موثوق. بالـreflected XSS، القيمة بتيجي ضمن الطلب وبتنعكس مباشرة بالجواب؛ غالباً الضحية لازم تفتح رابطاً محضّراً. بالـstored XSS، التعليق أو الملف الشخصي بينحفظ وبعدين بينعرض لزوار آخرين، فممكن يصيب كثير مستخدمين. بالـDOM-based XSS، كود JavaScript بالمتصفح ياخد قيمة مثل جزء من الرابط ويحطها بمكان DOM غير آمن، وممكن الخادم ما يرسل HTML ضاراً أصلاً.

## الترميز حسب السياق

لأن المتصفح يثق بكود الموقع ضمن الأصل نفسه، ممكن الكود المحقون يعمل إجراءات بصلاحيات المستخدم أو يعرض واجهة مزيفة. الحل الأساسي ترميز المخرجات حسب موضعها: نص HTML غير خاصية HTML أو JavaScript أو URL أو CSS. استخدم قوالب بترميز تلقائي وتجنّب نقاط DOM الخطرة؛ وإذا التطبيق يسمح HTML من المستخدم، استخدم منظّفاً موثوقاً بقواعد محددة. سياسة أمان المحتوى (Content Security Policy, CSP) بتقيّد مصادر السكربتات كطبقة دفاع إضافية، لكنها ما بتصلح الترميز الخاطئ. و`HttpOnly` يمنع قراءة الكوكي من JavaScript، لكنه ما يمنع سكربت XSS من إرسال طلبات باسم المستخدم. قارن مع [CSRF](topic:csrf): هناك المتصفح يُستدرج لإرسال طلب، وهنا كود المهاجم يعمل ضمن موقع الضحية.
