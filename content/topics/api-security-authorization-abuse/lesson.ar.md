## ليش API إلها نموذج تهديد خاص؟

مصطلحات: **authentication** (_kimlik doğrulama_)، **authorization** (_yetkilendirme_)، **BOLA** (_nesne düzeyi yetkilendirme açığı_)، و**BFLA** (_işlev düzeyi yetkilendirme açığı_).

واجهة الموقع بتحدد شو الأزرار اللي بتظهر للمستخدم، بس تطبيق API بيستقبل طلبات مباشرة من عميل ممكن يتحكم بالمسار والرؤوس والجسم. إخفاء زر الإدارة بالواجهة ما بيعني إن الخادم منع استدعاء الوظيفة. لذلك لازم الخادم يطبق التحقق من الهوية (authentication) والتفويض (authorization) على كل طلب، ويتعامل مع الحقول والحدود والموارد على أساس أن العميل غير موثوق.

يعرض الكتاب قائمة مخاطر API من عشرة أصناف: صلاحية الكائن (BOLA)، مصادقة ضعيفة، صلاحية خصائص الكائن، استهلاك موارد غير محدود، صلاحية الوظيفة (BFLA)، إساءة استخدام تدفقات العمل الحساسة، SSRF، سوء إعداد الأمان، نقص جرد الواجهات، واستهلاك غير آمن لخدمات API خارجية. أسماء القائمة وإصدارها كما بالكتاب؛ الفكرة هنا التصنيفات والآليات، لا الادعاء بأنها ترتيب حديث.

## Authentication ليست Authorization

التحقق من الهوية يجيب «مين المستخدم؟»؛ التفويض يجيب «هل مسموح له يعمل هالعملية على هالشيء؟». ثغرة التفويض على مستوى الكائن (Broken Object Level Authorization, BOLA)، المعروفة أيضاً بسياق IDOR، بتحصل إذا الخادم يتحقق أن الرمز صالح لكنه ما يفحص إن المستخدم يملك الحساب المطلوب. تغيير معرّف كائن في الطلب قد يكشف بيانات مستخدم آخر. السبب الجذري هو غياب فحص الصلاحية على الخادم لكل كائن؛ طريقة استغلاله قد تكون تخمين معرّفات، لكن المعرفات العشوائية وحدها لا تصلح الخلل إذا تسرب المعرف.

التفويض على مستوى الوظيفة (Broken Function Level Authorization, BFLA) مختلف: المستخدم يصل لوظيفة إدارية لا يملكها، مثل حذف مستخدم أو منح دور. في BOLA الوظيفة نفسها مسموحة لكن على كائن شخص آخر؛ في BFLA الوظيفة نفسها غير مسموحة للمستخدم. إخفاء الزر أو تغيير عنوان URL ليس دفاعاً. افحص هوية المستخدم ودوره وسياق الطلب في الخادم، وطبّق المنع افتراضياً.

## حقول الطلب والرد هي سطح صلاحيات أيضاً

**كشف بيانات زائد** يحدث إذا أعاد الخادم كل خصائص الكائن ثم توقع أن تخفي الواجهة الحقول الحساسة. البيانات وصلت للعميل فعلاً؛ لذلك أنشئ تمثيلاً صريحاً لكل endpoint وأرسل أقل الحقول المطلوبة. أما **mass assignment** فيحدث عند نسخ حقول JSON الواردة تلقائياً إلى كائن قاعدة البيانات؛ إضافة `role` أو `balance` غير مسموح قد تغير امتيازاً أو قيمة حساسة. استخدم قائمة حقول مسموحة للكتابة، وافصل مخطط إدخال المستخدم عن نموذج التخزين.

## JWT: تحقق من سياسة الخادم

يتكون JWT التقليدي من header وpayload وsignature مفصولة بنقاط. أجزاء header وpayload بترميز Base64URL وليست مشفرة؛ التوقيع يساعد على كشف التعديل، لكنه لا يخفي البيانات. لا تضع أسراراً في payload.

الخادم لا يختار سياسة التحقق من `alg` الذي يرسله العميل. ثبّت الخوارزمية والمفتاح المتوقعين في إعداد موثوق، وارفض `none` وأي خوارزمية غير مسموحة. خلط الخوارزميات يصبح خطراً إذا التنفيذ يفسر مفتاحاً أو خوارزمية بطريقة غير متوافقة مع السياسة؛ لذلك لا تعتمد على عنوان عام يقول إن كل مكتبة أو إصدار يقبل السيناريو ذاته. افحص التوقيع فعلياً، و`exp`، و`iss` (المُصدر)، و`aud` (الجمهور)، والادعاءات المطلوبة مثل `sub` و`iat` بحسب سياسة التطبيق. هذا امتداد لموضوع [التحقق من JWT](topic:jwt-validation): التوقيع الصحيح وحده لا يثبت أن الرمز مخصص لهذه الخدمة أو ما زال صالحاً.

## المصادقة، تحديد المعدل، واستهلاك الموارد

مصادقة API الضعيفة تشمل غياب حدود محاولات الدخول، رموزاً متوقعة أو طويلة العمر بلا إبطال، رموزاً في URL قد تظهر في السجل أو سجل المتصفح، واستعادة حساب ضعيفة. في هجوم تعبئة بيانات الاعتماد (credential stuffing) يجرب الخصم أزواجاً مسربة من خدمات أخرى، مستفيداً من إعادة استخدام كلمات المرور. خفف ذلك بتحديد معدل عند الحساب وعنوان الشبكة، رصد السلوك الشاذ، MFA عند الحاجة، رموز قصيرة العمر وقابلة للإلغاء، واستجابة استعادة آمنة.

دلو الرموز (token bucket) نموذج لتحديد المعدل: السعة `b` تحدد الاندفاع المسموح، ويُعاد ملء الدلو بمعدل `r` رمزاً في الثانية، وكل طلب يستهلك رمزاً؛ إذا لم يوجد رمز يُرفض الطلب. المتوسط طويل الأجل يقارب `r` والاندفاع القصير محدود بـ`b`. في نظام موزع يجب أن تكون الحالة مشتركة أو متناسقة بين الخوادم؛ وحدّ لكل IP فقط يمكن تجاوزه بتوزيع المحاولات، وقد يظلم مستخدمين خلف NAT، لذا اختر مفاتيح وحدوداً مناسبة لكل عملية. حدود GraphQL ينبغي أن تراعي كلفة الاستعلام وليس عدد الطلبات فقط.

## REST وGraphQL ومخزون الواجهات

REST يملك عادة مسارات كثيرة؛ الخطأ قد يكون endpoint نُسي فيه فحص BOLA أو BFLA. GraphQL يجمع الاستعلامات في نقطة واحدة ويمنح العميل مرونة اختيار الحقول، لكنه قد يسمح بطلب متداخل عميق أو مكلف يستهلك موارد كبيرة. ضع حد عمق وكلفة، وطبّق التفويض على كل حقل/كائن، وراجع introspection في الإنتاج بحسب احتياجك؛ إيقافه لا يعوض التفويض. النموذجان يحتاجان حدود حجم ومهلة ومراقبة.

الواجهات الظلية (shadow APIs) غير الموثقة أو غير المعروفة لفريق الحماية، والواجهات الزومبي (zombie APIs) إصدارات قديمة ما زالت تعمل. قد يملك الإصدار القديم تحققاً أضعف من الجديد. احتفظ بجرد محدث للمالكين والإصدارات والبيانات، واختبر الإصدارات القديمة وأوقفها بخطة معلنة. وعند استهلاك API لطرف ثالث، تحقق من TLS والبيانات والوجهة والصلاحيات؛ الثقة بالمزود لا تجعل استجابته مدخلاً موثوقاً.

## CORS ليس نظام تفويض

سياسة نفس المصدر (Same-Origin Policy) تحد من قراءة JavaScript لردود مصدر آخر. CORS يتيح للخادم السماح لمصادر محددة بالقراءة عبر المتصفح. إذا كان الخادم يعكس أي قيمة `Origin` ويتيح credentials، فقد يسمح لموقع خبيث بقراءة الرد ضمن جلسة الضحية في شروط المتصفح ذات الصلة. الحل قائمة أصل دقيقة، ومطابقة كاملة scheme/host/port؛ لا تستخدم اختباراً جزئياً مثل «يحتوي اسم النطاق».

CORS يتحكم بما يستطيع JavaScript قراءته، ولا يمنع كل أنواع إرسال الطلبات العابرة للمواقع؛ لذلك لا يحل محل حماية [CSRF](topic:csrf). كمان CORS لا يعوض التفويض: عميل غير متصفح يستطيع إرسال الطلب مباشرة. ضع لكل طبقة سؤالها: هل هوية المستخدم صحيحة؟ هل يملك صلاحية الكائن والوظيفة؟ هل أصل المتصفح مسموح؟ وهل الطلب يستهلك موارد معقولة؟

**إضافة تعليمية:** راجع كل endpoint مع مصفوفة (الدور × العملية × الكائن × الحقول)، ثم اختبر الرفض الافتراضي. هالمنهج بيوضح الفرق بين جذور الثغرات وطرق كشفها، وبيمنع اعتبار قائمة OWASP بديلاً عن تحليل تدفق التطبيق.
