## التفويض مش هوية المستخدم

OAuth بيعطي تطبيقاً صلاحية محدودة للوصول لمورد نيابة عن المستخدم؛ رمز الوصول ما بيقول لوحده مين المستخدم. OpenID Connect (OIDC) بيضيف طبقة مصادقة فوق OAuth 2.0، وبيرجع ID token يحمل ادعاءات الهوية ضمن سياق موثوق. SAML كمان يُستخدم لاتحاد الهوية، لكن بصيغة XML. الاختيار مرتبط بالسؤال: API وصلاحية مفوضة؟ OAuth. «مين سجّل الدخول؟» OIDC. نظام مؤسسي قائم؟ ممكن SAML. ارجع لـ[OAuth](topic:oauth-authorization) و[SSO والفيدرالية](topic:sso-kerberos-federation).

## أجزاء JWT وما لا تعنيه

JWT غالباً بيتكون من ثلاث سلاسل Base64URL مفصولة بنقط: header.payload.signature. الرأس يذكر النوع وخوارزمية التوقيع؛ الحمولة تحمل claims مثل `sub` للموضوع، `iss` للجهة المصدرة، `aud` للجهة المستقبلة، و`exp` لانتهاء الصلاحية. التوقيع يكشف التلاعب إذا تحقق بطريقة صحيحة. ترميز Base64URL مو تشفير: أي حامل يقدر يقرأ الحمولة، فلا تحط فيها كلمة مرور أو سر. التوقيع يحمي الأصالة/السلامة، مش السرية؛ يمكن استخدام تنسيق مشفر منفصل عند الحاجة وبحسب البروتوكول.

## ما بعد بنية الرمز

تحليل JWT وقراءة claims لا يكفيان لقبوله. لازم الخادم يتحقق من التوقيع وسياق الجهة والجمهور والصلاحية؛ التفاصيل والهجمات الشائعة مشروحة في [التحقق الآمن من JWT](topic:jwt-validation). لا تستخدم ID token كـaccess token أو العكس، ولكل واحد جمهور وغرض مختلف. JWT الموقع ذاتياً لا يُلغى تلقائياً من كل مكان قبل انتهاء صلاحيته، لذلك عمره وإدارته جزء من [أمن الجلسة](topic:session-security).

_ملاحظة تقنية:_ JWT ليس مرادفاً للتشفير ولا «هوية» تلقائياً؛ معناه يعتمد على الجهة التي أصدرته، الجمهور، الغرض والتحقق المنفذ.

**مصطلحات English → Türkçe:** `ID token` (Kimlik belirteci), `claim` (İddia), `issuer` (Düzenleyen), `audience` (Hedef kitle), `expiry` (Son kullanma), `JSON Web Token` (JSON Web Belirteci).
